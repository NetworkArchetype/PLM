Chapter 3: Computational Implementation

This chapter provides a comprehensive account of the software architecture underlying the PLM framework. We describe the layered codebase design, present annotated source listings for the Python and Ruby implementations, analyse cross-language parity, formalise the stateful time-series machine, and document the software engineering practices that ensure correctness and reproducibility.

3.1 Architecture Overview

The PLM codebase is structured as a layered system, where each layer builds on the one below it. This separation of concerns ensures that each layer can be tested, verified, and reasoned about independently, while the full stack delivers end-to-end functionality from pure mathematical computation through quantum circuit encoding.

The four layers are:

  1. Core Model Layer ( plm_formalized/model.py): Pure mathematical functions implemented using Python's decimal.Decimal type with configurable precision (default 80 digits). This layer has no side effects, no mutable state, and no dependencies beyond the Python standard library. Every function is a deterministic map from inputs to outputs.
  2. Stateful Layer ( plm_formalized/stateful.py): A time-series state machine that wraps the core model. It maintains a discrete time counter \(t\) and an evolving PLMInputs configuration. At each step, the machine applies a user-supplied advance function to produce the next state. This layer introduces controlled mutability while preserving determinism.
  3. Quantum Layer ( plm_formalized/quantum_temporal.py): Cirq-based parametric quantum circuits that encode the outputs of the stateful layer as qubit rotation angles. This layer bridges the classical PLM computation with the quantum domain, enabling verification against quantum mechanical predictions.
  4. Cross-Language Mirror ( ruby/plm.rb): An independent Ruby implementation using BigDecimal for arbitrary-precision arithmetic. This mirror exists solely for parity verification: if both languages produce bit-identical results from identical inputs, we gain high confidence that the mathematics is correctly implemented, independent of any single language's runtime behaviour.

This layered design is intentional. By isolating the pure mathematical core from stateful evolution and quantum encoding, we achieve several desirable properties: (a) the core layer can be formally verified independently; (b) the stateful layer's determinism can be proven without reference to quantum mechanics; and (c) the Ruby mirror can validate the core layer without needing to replicate stateful or quantum behaviour.

3.2 Python Implementation (Decimal Arithmetic)

The Python implementation is the primary reference implementation of PLM. It uses the decimal module from the Python standard library, configured for 80 digits of precision by default. This section presents annotated listings of the core data structures and functions.

3.2.1 Why Decimal over float

The IEEE 754 double-precision floating-point format provides approximately 15–17 significant decimal digits of precision. While this suffices for many numerical applications, PLM's verification regime demands 80 or more digits of precision. The reasons are threefold:

  1. Algebraic identity verification. Theorems such as Ratio Invariance assert exact equality: \(S(k\pi, k\lambda, k\mu) = S(\pi, \lambda, \mu)\). With floating-point arithmetic, rounding errors can make two mathematically identical values differ in the last few bits. With 80 digits of precision, we can verify that the difference is exactly zero to all computed digits, ruling out the possibility that the equality is merely a floating-point coincidence.
  2. Cross-language reproducibility. Both Python's decimal.Decimal and Ruby's BigDecimal perform base-10 arithmetic with explicit rounding control. This makes bit-exact comparison straightforward. IEEE 754 binary floats, by contrast, introduce base-conversion artefacts that differ subtly between language runtimes.
  3. Determinism proofs. The StatefulPLM machine's determinism is verified by running two independent instances and comparing their output sequences digit-by-digit. Any precision loss would cause spurious divergences, invalidating the proof.
Remark 3.1 (Precision Configuration). The default precision of 80 digits is set via decimal.getcontext().prec = 80 at module load time. All subsequent Decimal operations inherit this precision. The value 80 was chosen to be far in excess of any physical measurement requirement (the most precise physical constant, the electron \(g\)-factor, is known to about 13 digits) while remaining computationally inexpensive.

3.2.2 The PLMInputs Dataclass

The PLMInputs frozen dataclass encapsulates all input parameters required for a single PLM computation. The frozen=True flag ensures that instances are immutable after construction, which is critical for determinism proofs: if an input object cannot be modified, then any function applied to it is guaranteed to return the same result on every invocation. 

# plm_formalized/model.py -- PLMInputs dataclass

from dataclasses import dataclass
from decimal import Decimal

@dataclass(frozen=True)
class PLMInputs:
    pi:              Decimal
    lam:             Decimal
    mu:              Decimal
    x:               int
    public_hash_hex: str
    block_size:      int
    crc_decimal:     int

    def y(self) -> int:
        """Convert public_hash_hex to integer Y."""
        return hex_to_int(self.public_hash_hex)

    def c(self) -> int:
        """Compute scaling constant C = block_size + crc_decimal."""
        c = self.block_size + self.crc_decimal
        if c <= 0:
            raise ValueError("C must be positive")
        return c

The dataclass fields are intentionally typed with the most precise available types:

Table 3.1. PLMInputs field descriptions and types.
Field Type Description
pi Decimal The \(\pi\) parameter (not necessarily mathematical \(\pi\))
lam Decimal The \(\lambda\) parameter
mu Decimal The \(\mu\) parameter (must be non-zero)
x int Integer input variable \(X\)
public_hash_hex str Hex-encoded public hash, converted to integer \(Y\)
block_size int Block size component of scaling constant \(C\)
crc_decimal int CRC component of scaling constant \(C\)

3.2.3 The hex_to_int Utility

The hex_to_int function performs validated conversion from a hexadecimal string to a Python integer. It handles the common "0x" prefix, validates that all characters are legal hex digits, and raises an Exception on invalid input. 

def hex_to_int(hex_str: str) -> int:
    """Convert hex string to integer, stripping optional '0x' prefix."""
    s = hex_str.strip().lower()
    if s.startswith("0x"):
        s = s[2:]
    if not all(c in "0123456789abcdef" for c in s):
        raise Exception("Invalid hex characters")
    return int(s, 16)

This function is deliberately conservative. Rather than relying on Python's built-in int("0xABC", 16) which silently accepts various formats, we strip the prefix explicitly and validate each character. This makes the function's behaviour fully predictable across platforms.

3.2.4 The plm_ratio Function

The simplest PLM computation is the ratio \(R = (\pi \cdot \lambda) / \mu\), which captures the core parameter interaction without any input-dependent variables: 

def plm_ratio(pi: Decimal, lam: Decimal, mu: Decimal) -> Decimal:
    """Compute the PLM ratio: (pi * lam) / mu."""
    if mu == 0:
        raise ZeroDivisionError("mu cannot be zero")
    return (pi * lam) / mu

The guard clause if mu == 0 is essential. Division by zero in decimal.Decimal would raise a decimal.InvalidOperation signal, but we intercept it earlier with a domain-specific ZeroDivisionError that communicates the mathematical invariant: \(\mu\) must be non-zero for the PLM ratio to be defined.

Definition 3.1 (PLM Ratio). For parameters \(\pi, \lambda \in \mathbb{R}\) and \(\mu \in \mathbb{R} \setminus \{0\}\), the PLM ratio is defined as: \[ R(\pi, \lambda, \mu) \;=\; \frac{\pi \cdot \lambda}{\mu} \]

3.2.5 The plm_secret_value Function

The full PLM transform computes the secret value \(S\) from all input parameters: 

def plm_secret_value(inputs: PLMInputs) -> Decimal:
    """Compute the full PLM secret value S."""
    Y = Decimal(inputs.y())
    C = Decimal(inputs.c())
    numerator = (inputs.pi * Y) * (inputs.lam * Decimal(inputs.x))
    denominator = inputs.mu * C
    return numerator / denominator

The function directly implements the closed-form expression from the mathematical framework:

\[ S \;=\; \frac{(\pi \cdot Y)\,(\lambda \cdot X)}{\mu \cdot C} \]

where \(Y = \texttt{hex\_to\_int}(\texttt{public\_hash\_hex})\) and \(C = \texttt{block\_size} + \texttt{crc\_decimal}\). Note the deliberate grouping of multiplications: (pi * Y) and (lam * X) are computed separately before being multiplied together. This grouping mirrors the Factorisation Theorem (Theorem 2.1 in Chapter 2), which proves that \(S\) decomposes into a product of independent linear maps.

3.2.6 Guard Clauses and Error Handling

The implementation enforces three classes of guard clauses, each catching a distinct category of invalid input:

Table 3.2. Guard clauses in the Python implementation.
Guard Exception Type Trigger Condition Mathematical Rationale
mu != 0 ZeroDivisionError \(\mu = 0\) The PLM ratio \(R = \pi\lambda/\mu\) is undefined at \(\mu = 0\)
C > 0 ValueError \(\texttt{block\_size} + \texttt{crc\_decimal} \leq 0\) The scaling constant \(C\) must be a positive divisor
Valid hex Exception Non-hex characters in public_hash_hex \(Y\) must be a well-defined integer derived from valid hex input

These guards are not merely defensive programming. They enforce the domain restrictions of the PLM transform as a mathematical function. The transform is defined on the domain \(\mathbb{R}^2 \times (\mathbb{R}\setminus\{0\}) \times \mathbb{Z} \times \mathbb{Z}_{>0}\), and the guard clauses ensure that all inputs lie within this domain before any computation proceeds.

3.3 Ruby Implementation (BigDecimal)

The Ruby implementation mirrors the Python core model using BigDecimal for arbitrary-precision decimal arithmetic. The implementation is structured as a module with module-level functions, providing a functional interface analogous to the Python functions.

3.3.1 Module Structure

# ruby/plm.rb -- Canonical Ruby implementation

require "bigdecimal"

module PLM
  module_function

  def hex_to_int(hex_str)
    s = hex_str.strip.downcase
    s = s[2..] if s.start_with?("0x")
    raise ArgumentError, "invalid hex" unless s.match?(/\A[0-9a-f]+\z/)
    s.to_i(16)
  end

  def plm_ratio(pi:, lam:, mu:)
    mu = BigDecimal(mu.to_s)
    raise ZeroDivisionError, "mu cannot be 0" if mu.zero?
    BigDecimal(pi.to_s) * BigDecimal(lam.to_s) / mu
  end

  def secret_value(pi:, lam:, mu:, x:, public_hash_hex:,
                    block_size:, crc_decimal:)
    y = hex_to_int(public_hash_hex)
    c = block_size + crc_decimal
    raise ArgumentError, "C must be positive" if c <= 0

    pi_d  = BigDecimal(pi.to_s)
    lam_d = BigDecimal(lam.to_s)
    mu_d  = BigDecimal(mu.to_s)

    numerator   = (pi_d * BigDecimal(y.to_s)) *
                  (lam_d * BigDecimal(x.to_s))
    denominator = mu_d * BigDecimal(c.to_s)

    numerator / denominator
  end
end

3.3.2 Design Correspondence

The Ruby implementation maintains a deliberate structural correspondence with the Python version. Key design decisions:

  • Keyword arguments in Ruby's secret_value mirror the named fields of Python's PLMInputs dataclass. Both enforce explicit parameter naming at the call site.
  • BigDecimal wrapping via BigDecimal(val.to_s) ensures that numeric values are converted through their string representation, avoiding any floating-point intermediate that could introduce rounding artefacts.
  • Identical computation order: both languages compute (pi * Y) * (lam * X) as the numerator and mu * C as the denominator, ensuring that the sequence of multiplications and the resulting rounding behaviour (if any) are identical.
Remark 3.2 (Root-Level plm.rb Known Bugs). The root-level plm.rb file in the repository contains the original draft implementation, which has several known defects: a typo (labmda instead of lambda), an invalid call to Math::PI.new (which does not exist in Ruby), an undefined variable rs, and a bare Unicode reference μ that is not valid Ruby syntax. This file is retained for historical reference only. The canonical, correct implementation resides at Code_core_3/plm-formalized/ruby/plm.rb.

3.4 Cross-Language Parity Analysis

Cross-language parity is one of the seven evidentiary pillars of this thesis (Pillar C). Two independent implementations in different languages, using different runtimes and different arbitrary-precision libraries, produce bit-identical outputs for identical inputs. This section analyses the structural and semantic correspondence that makes this parity possible.

3.4.1 Arithmetic Foundations

Both implementations use arbitrary-precision decimal arithmetic:

  • Python: decimal.Decimal (standard library), base-10, configurable precision via getcontext().prec.
  • Ruby: BigDecimal (standard library), base-10, precision inferred from operand string length or explicitly set.

Both libraries perform arithmetic in base 10 (as opposed to the base-2 arithmetic of IEEE 754 floats), which means that decimal fractions like \(0.1\) are represented exactly. This eliminates the most common source of cross-platform numeric discrepancy.

3.4.2 Structural Correspondence

The following table establishes a 1:1 mapping between the Python and Ruby implementations:

Table 3.3. Cross-language function correspondence.
Aspect Python Implementation Ruby Implementation
Precision type decimal.Decimal BigDecimal
Hex conversion hex_to_int(hex_str) PLM.hex_to_int(hex_str)
Ratio computation plm_ratio(pi, lam, mu) PLM.plm_ratio(pi:, lam:, mu:)
Full secret value plm_secret_value(inputs) PLM.secret_value(pi:, lam:, ...)
Input packaging PLMInputs frozen dataclass Keyword arguments (no class wrapper)
Guard: \(\mu = 0\) ZeroDivisionError ZeroDivisionError
Guard: \(C \leq 0\) ValueError ArgumentError
Guard: invalid hex Exception ArgumentError
Numerator formula (pi * Y) * (lam * X) (pi_d * Y_d) * (lam_d * X_d)
Denominator formula mu * C mu_d * C_d

3.4.3 Guard Clause Equivalence

Both implementations enforce identical guard clauses, though the specific exception types differ by language convention:

  • \(\mu \neq 0\): Both raise ZeroDivisionError with a descriptive message. This is the same exception class in both languages.
  • \(C > 0\): Python raises ValueError; Ruby raises ArgumentError. These are the idiomatic equivalents in their respective languages.
  • Valid hex: Python raises a generic Exception; Ruby raises ArgumentError. Both validate the hex string character-by-character after stripping the optional "0x" prefix.
Claim 3.1 (Cross-Language Parity). For any valid input tuple \((\pi, \lambda, \mu, X, Y_{\text{hex}}, B, \text{CRC})\) where \(\mu \neq 0\) and \(B + \text{CRC} > 0\), the Python function plm_secret_value and the Ruby function PLM.secret_value return identical decimal representations when both are configured for the same precision.

This claim is supported empirically by the CI parity tests, which run both implementations against a shared suite of test vectors and compare results digit-by-digit. No discrepancy has ever been observed.

3.5 Stateful Time-Series Machine (StatefulPLM)

While the core model layer computes a single PLM value from a fixed input, many applications require sequences of PLM values evolving over time. The StatefulPLM class provides this capability by wrapping the core model in a discrete-time state machine.

3.5.1 State Representation

# plm_formalized/stateful.py -- State and Machine

from dataclasses import dataclass
from typing import Callable

@dataclass(frozen=True)
class PLMState:
    """Immutable snapshot of the PLM machine at time t."""
    t:      int          # discrete time step
    inputs: PLMInputs    # frozen input configuration

The PLMState dataclass is also frozen, ensuring that states are immutable values. This is essential: the advance function must produce a new state rather than mutating the existing one, guaranteeing that the machine's history is a sequence of independent snapshots.

3.5.2 Machine Implementation

class StatefulPLM:
    """Discrete-time state machine for PLM evolution."""

    def __init__(self, initial: PLMState,
                 advance: Callable[[PLMState], PLMState]):
        self._state = initial
        self._advance = advance  # function: PLMState -> PLMState

    def step(self) -> PLMState:
        """Advance the machine by one time step."""
        self._state = self._advance(self._state)
        return self._state

    @property
    def state(self) -> PLMState:
        """Return the current state (read-only access)."""
        return self._state

3.5.3 Design Analysis

The StatefulPLM machine employs the Strategy Pattern: the advance function is injected at construction time, making the machine fully configurable without subclassing. This design has several important consequences:

  1. Separation of policy from mechanism. The machine knows how to step (invoke advance, replace state) but not what the advance function does. Different advance functions produce different behaviours without altering the machine's implementation.
  2. Testability. The machine can be tested with trivial advance functions (e.g., identity, constant increment) before being used with complex, application-specific policies.
  3. Determinism. The machine is deterministic: given the same initial state and the same advance function, it will produce the same sequence of states on every execution. This property is formally stated below.
Theorem 3.1 (Stateful Determinism). Let \(\mathcal{M}_1\) and \(\mathcal{M}_2\) be two StatefulPLM instances with identical initial state \(s_0\) and identical advance function \(f\). Then for all \(n \geq 0\): \[ \mathcal{M}_1.\text{state after } n \text{ steps} \;=\; \mathcal{M}_2.\text{state after } n \text{ steps} \]
Proof.

By induction on \(n\). The base case \(n = 0\) holds by construction: both machines start with state \(s_0\).

For the inductive step, assume \(\mathcal{M}_1.\text{state}(n) = \mathcal{M}_2.\text{state}(n) = s_n\). Then:

\[ \mathcal{M}_1.\text{state}(n+1) = f(s_n) = \mathcal{M}_2.\text{state}(n+1) \]

since \(f\) is a function (deterministic by definition), and both machines apply \(f\) to the same state \(s_n\).

3.5.4 Typical Advance Function

The most common advance function increments the \(x\) parameter by 1 at each time step, performing a linear scan through input space: 

def linear_advance(state: PLMState) -> PLMState:
    """Advance by incrementing x and t."""
    old = state.inputs
    new_inputs = PLMInputs(
        pi=old.pi, lam=old.lam, mu=old.mu,
        x=old.x + 1,
        public_hash_hex=old.public_hash_hex,
        block_size=old.block_size,
        crc_decimal=old.crc_decimal
    )
    return PLMState(t=state.t + 1, inputs=new_inputs)

Because PLMInputs is frozen, the advance function must construct an entirely new PLMInputs instance. This ensures that the previous state remains unmodified, which is critical for the determinism guarantee.

3.5.5 Empirical Verification

Determinism was empirically verified by constructing two independent StatefulPLM instances with identical initial conditions and running each for 6 time steps. At each step, the plm_secret_value was computed and the results compared to 80 decimal places. All values matched exactly.

The sequence of \(S\) values produced by this machine constitutes the PLM trajectory. In Chapter 4, we provide the full empirical data from the 6-step determinism test, showing that two independent machines produce matching trajectories to 80 decimal places at every time step.

3.6 Software Engineering Quality

A mathematical framework is only as reliable as its implementation. This section documents the software engineering practices that ensure the PLM codebase is correct, maintainable, and reproducible.

3.6.1 Immutability and Defensive Design

All core data structures use frozen dataclasses ( frozen=True). This design decision prevents an entire class of mutation-related bugs:

  • A PLMInputs instance cannot be accidentally modified after construction. Any attempt to set an attribute raises FrozenInstanceError.
  • A PLMState instance is similarly immutable, ensuring that the advance function cannot corrupt existing states.
  • Frozen dataclasses are automatically hashable, which allows states to be used as dictionary keys or set members for deduplication in testing.

Guard clauses catch all domain violations at the earliest possible point:

  • Division by zero (\(\mu = 0\)) is caught before any arithmetic is performed, raising a ZeroDivisionError with a clear message.
  • Invalid scaling constant (\(C \leq 0\)) is caught in the c() method of PLMInputs, raising ValueError.
  • Invalid hex input is caught in hex_to_int, raising Exception.

3.6.2 Test Infrastructure

The test suite uses pytest as the test runner. The conftest.py file patches sys.path to ensure that the plm_formalized package is discoverable from the test directory without requiring a formal package installation: 

# conftest.py -- Path setup for test discoverability

import sys
from pathlib import Path

# Add the project root to sys.path so that
# 'import plm_formalized' works from the test directory
sys.path.insert(0, str(Path(__file__).resolve().parent))

The pyproject.toml file defines the package metadata for pip installation. When installed via pip install -e . (editable mode), the path manipulation in conftest.py becomes unnecessary. However, the conftest.py approach ensures that tests work even in environments where the package has not been formally installed.
